Why every agent conversation needs a governed beginning and a deliberate end — and how a disciplined thread turns into durable memory.

Series note
This paper is the direct sequel to Agent Memory, which established the three-tier memory model — episodic, semantic, and procedural — as the missing layer in most agent deployments. That paper made the case for what to accumulate. This paper addresses the mechanism that makes accumulation possible: the thread. Without a governed thread lifecycle, memory does not compound.
Foundations
Thread is a production primitive of agent implementation. The thread as a named, addressable conversation unit is already a first-class construct in the leading agentic frameworks. This paper's contribution is not the thread itself — it is the governance layer (GCI and GCT) that most framework implementations currently leave to the developer, and the argument that this governance gap is the missing precondition for memory to compound.
Zeigarnik effect — incomplete tasks occupy greater cognitive load than completed ones (Zeigarnik, 1927). The psychological grounding for why ungoverned thread endings create residual cognitive burden for users, and why deliberate closure, like turning a page, produces genuine relief rather than mere convenience.
LangGraph — thread as a checkpointed execution unit identified by thread_id; state persisted after every node transition and resumable across restarts. docs.langchain.com/oss/python/langgraph/persistence
OpenAI Assistants API / Responses API — Thread (now migrating to Conversation in the Responses API) as a persistent container for messages and runs, with automatic context-window truncation. developers.openai.com/api/docs/assistants/deep-dive
Contextual Memory Virtualisation (CMV) — DAG-based state management treating conversation state as a version-controlled resource, with snapshot, branch, and trim primitives (Santoni, Imperial College London, arXiv:2602.22402, 2026). Grounds the thread branching model in Section 06.
Mastra — thread identified by thread (conversation ID) and resource (owning user or entity); provides createThread(), saveThread(), and summarizeThread() lifecycle methods. mastra.ai/docs/memory/threads-and-resources

01 — The missing mechanism

Why memory needs
a container

A thread is the boundary of the living context window of an agent. Memory is its persisted context, stored in vectorized and indexed form. It is centred on one meaningful conversation among user, system (tools), and agent. As the conversation grows, so does the thread's state machine and context window, until at some point it requires summarisation and reduction so the underlying language model can continue to process reasoning calls effectively. A thread carries a permanent identifier, which makes it addressable, resumable, and attributable across its entire lifecycle. These are not implementation details. They are what transform a list of messages into a unit of memory production.

Most products treat the thread as a passive container: messages accumulate, the context window fills, and eventually the conversation disappears into a scrollable history that no system reads again. The memory architecture described in Paper 1 cannot be built on this foundation. You cannot extract episodic value from a conversation that never had a clear sign of closure, and you cannot distil semantic knowledge from interactions that never reached semantic completion.

A thread without a governed beginning is a conversation that doesn't know what it's for. A thread without a governed end is institutional knowledge that was never collected.

This paper introduces two mechanisms — Governed Conversation Initiation (GCI) and Governed Conversation Termination (GCT) — that together give a thread the structure it needs to become a memory-producing unit. GCI gives the thread purpose before the first message is sent. GCT gives it a deliberate ending that triggers the memory pipeline. Between them, the thread becomes a first-class architectural primitive rather than an incidental by-product of a chat interface.

02 — The thread

A flow state machine,
not a chat log

A thread is a stateful unit with a defined flow — an identity, a lifecycle of transitions, and a memory pipeline attached to its terminal state. Every conversation an agent has belongs to a thread. Every thread moves through a defined sequence of states via explicit transitions. Those transitions are not cosmetic — they carry information. The move to Active means intent is established. The move to Closed means a unit of work is complete and value is ready to harvest.

03 — GCI

Governed Conversation
Initiation

An agent that opens with a blank chatbox signals unlimited capability — no frame, no goal, no context — leaving users with no basis for calibrating expectations, and producing either paralysis or misuse. Hint text patches the symptom. Governed Conversation Initiation addresses the cause: it is the design layer that establishes the frame for a thread before the first user message is sent. Not a form, not onboarding — a lightweight, purposeful gesture that gives the agent structured intent from turn one. GCI produces three things the thread needs at open: a goal (what this conversation should accomplish), a context (what prior knowledge to inject), and a scope (what kind of work this is).

GCI must calibrate to the user, not impose a fixed weight of scaffolding on everyone: the two users below need very different things from the same initiation step.

Novice user
Needs orientation
  • Does not know what the agent can do or how to frame a request
  • Benefits from suggested thread archetypes drawn from real capabilities
  • Prior context injection surfaces relevant history they may not think to retrieve
  • Goal clarification on turn one prevents early misdirection
GCI principle: scaffold the intent, reduce ambiguity early
Expert user
Needs to start fast
  • Knows exactly what they want and wants zero friction before the first message
  • A direct typed goal satisfies GCI in one gesture — no templates needed
  • Memory injection can be automatic and silent rather than prompted
  • Goal clarification turn feels patronising — skip it when intent is clear
GCI principle: get out of the way, trust stated intent

Both users benefit from GCI, but the weight of its scaffolding should be inversely proportional to the clarity of the user's intent. The UX implementation of that calibration is territory for designers. The principle is fixed: every thread needs a goal, a context, and a scope before the agent begins the very first reasoning loop. How visibly that is established is a design variable, not a design question.

04 — GCT

Governed Conversation
Termination

GCT is the less familiar half of the pair. Most deployments have not needed to think about it yet: threads accumulate, users move on, and the conversation is left behind — unread, unfiled, forgotten. Every thread that ends this way is a decision or a resolved question the organisation will have to rediscover from scratch next time.

A close button is the straightforward UX answer, and it is the right one for user-initiated close. But it is only half the picture. A user who deliberately chooses to close a thread is doing something meaningful: they are affirming that a unit of work is complete. That explicit signal is high-quality data — a reward signal, in reinforcement learning terms. Threads closed with user intent should carry more epistemic weight in memory than threads that simply went idle. The other half is agent-proposed close: the agent reasons over the conversation's context and its own capability to infer that a thread is likely done, then surfaces that inference as a human-in-the-loop check.

The practical answer is not to choose between agent-proposed and user-initiated close — it is to design both, understand what each produces, and let context determine which fires.

Humans need closure. Bluma Zeigarnik showed in 1927 that incomplete tasks occupy our minds disproportionately. The relief of turning a page is not metaphorical. It is cognitive. A thread that closes well earns that relief.

Contextual close
Agent-proposed, HITL confirmed
  • Agent detects goal resolution, natural conversation conclusion, or domain shift and proposes close
  • Idle-close policy catches threads that were quietly abandoned
  • Human-in-the-loop confirmation required before memory pipeline fires — agent proposes, user or system approves
  • Reduces cognitive burden on user; closure happens without explicit action
Memory signal: moderate confidence — inferred completion
User-initiated close
Explicit, intentional signal
  • User actively affirms the thread is complete — the highest-quality termination signal available
  • Equivalent to a reward signal in RL: explicit human confirmation that this unit of work succeeded
  • Threads closed this way should carry elevated weight in episodic retrieval and semantic distillation priority
  • Design must make close feel like preserving, not discarding — the close receipt is the critical mechanism
Memory signal: high confidence — explicit human reward

The specific UX patterns that implement these two modes — how the agent proposes close, what the close receipt looks like, how continuation is offered — are design territory. What is fixed is that closure is what fires the memory pipeline, covered next.

05 — The memory pipeline

What fires
on close

When a thread closes — whether by agent proposal, user confirmation, or idle-close policy — GCT triggers the two-stage process below, converting the thread's conversational value into the structured memory stores described in Paper 1. This pipeline is the operational link between the thread and the three-tier memory architecture: without it, a closed thread's decisions and context are discarded rather than written to the episodic and semantic stores.

The GCT memory pipeline
01
GCT Close confirmed — metadata stamped
Thread ID, resource ID, goal label, timestamp, and close mode (agent-proposed, user-initiated, or idle) are stamped. Close mode travels as a confidence weight through every downstream step.
02
Episodic Vectorise and persist
Thread structured state is vectorised and written to the episodic store scoped to the owning resource. Full message history archived as historical chat — readable, auditable, available for reopen.
03
User signal Reward weighting applied
User-initiated close is an explicit reward signal. It elevates the thread's retrieval rank in episodic similarity search, prioritises its content in the semantic distillation queue, and fast-tracks decisions and patterns for human review.
04
Semantic Cleanroom distillation
Asynchronous pass strips org-, user-, and context-specific content. Survivors — validated facts, resolved patterns, reusable procedures — are written to the semantic store. User-signalled threads enter this queue first. Governance required: human gate for significant promotions.
05
GCT Close receipt surfaced
Decisions preserved, open questions carried forward, memory contributions listed. The receipt makes the pipeline's output visible — closing feels like completion, not disappearance.

The cleanroom step deserves particular care because it is where the most organisational value is created, and where the most risk lives. Unchecked, it can poison the semantic store with context-specific decisions that appear general, or encode one user's preferences as policy. The governance layer from Paper 1 applies directly here: human gate for significant promotions, controlled write access, regular drift detection. The cleanroom is fundamentally a governance problem, not a technical one — it just happens to need a technical implementation.

06 — Reopen and branch

Continuing where
you left off

Closing a thread does not mean abandoning its work. Returning to a topic — a research thread that produced a first draft, a decision thread whose context is needed for a follow-on task — is one of the most common patterns in real agent usage. GCT is designed with this in mind. A closed thread is preserved, not destroyed. Reopening is a defined state machine transition, and it requires deliberate context window management rather than naive history replay.

Minimal reopen
Structured state snapshot
  • Inject goal, decisions, open questions from closed thread's state
  • Add last N verbatim messages as immediate context
  • Agent resumes without replaying full history
Best for: resuming a paused task quickly
Summary reopen
Generated resume document
  • Generate structured resume from episodic record
  • What was achieved, what remains open, key decisions
  • Becomes opening system context of the new session
Best for: returning after a long gap
Selective reopen
On-demand retrieval
  • Thread history queried by similarity to current user turn
  • Relevant prior context surfaces as needed, not all at once
  • Agent continues as if context were always available
Best for: long, complex threads with many topics
Future work
Two open problems in thread architecture that fall outside the scope of this paper but warrant explicit acknowledgement.
Tree-based thread architecture — beyond simple reopen, the thread model supports branching: a thread with a rich shared context can be split into parallel child threads, each inheriting the parent's structured state and closing independently to trigger its own memory pipeline, with episodic records merged back into the parent or left standalone. This is thread-as-tree rather than thread-as-line, the direct practical application of the DAG-based contextual memory virtualisation model (Santoni, 2026) cited in the Foundations. The model raises unresolved design questions: how are child thread episodic records merged back into a parent without context collision? How are conflicting decisions across branches reconciled before semantic promotion? How does the reopen state machine handle a thread with multiple closed children? These are active design problems, not solved ones.
Context window drift — a thread opened months ago carried assumptions about the world — market conditions, org structure, a codebase state, a policy — that may no longer hold. The context window was accurate at open; it becomes stale through time even without new messages. This is distinct from context window size management: it is a validity problem. Reopened threads in particular must address whether inherited context should be validated against current memory stores before reasoning resumes. No framework currently handles this systematically.
07 — Implications

Strategic implications

GCI and GCT determine whether the memory architecture from Paper 1 actually accumulates anything. The principles below follow directly from the framework developed across both papers in this series.

P1
Design GCI before you design the chat interface
The blank chatbox forecloses memory before the first message is sent. Decide how the thread will be initiated — its goal, injected context, and scope — before choosing a chat UI. GCI can be as minimal as a single agent behaviour on turn one, but it must be deliberate and calibrated to the user's level of intent, not uniform for everyone.
P2
Design both close modes — they produce different memory signal quality
Agent-proposed and user-initiated close are complementary, not alternatives. Build agent-proposed close as the default, friction-reducing path; build user-initiated close as a deliberate contribution act with a visible close receipt; treat idle-close as the safety net. Weight them differently in the memory pipeline — user close is a reward signal, not just a termination event.
P3
Make the memory pipeline visible through the close receipt
A silent memory pipeline gives users no evidence it did anything, and no incentive to close deliberately. The close receipt makes that output tangible, and builds the trust that drives future user-initiated closes — "the agent remembered what I decided" only lands if the user knows that closing the thread is what made it possible.
P4
Govern the cleanroom — it is the most consequential step
The episodic-to-semantic distillation pass turns thread-level knowledge into organisational knowledge — and is where errors compound, private context leaks into shared stores, or one user's pattern gets encoded as policy. Apply Paper 1's governance principles here: human gate for significant promotions, controlled write access, regular drift detection. Prioritise user-signalled threads in the queue — their higher confidence makes them the safest candidates for promotion.
P5
Thread quality determines memory quality — upstream
Memory quality is capped by thread quality: a thread without a stated goal produces unclear episodic records, one that compacted poorly loses its decisions, one never closed produces nothing. GCI and GCT are upstream investments — the data-hygiene equivalent for memory architecture — so invest in them before the memory layer accumulates noise, not after.
